# knowledge/ — 過去コンテストの分析とテクニック（現在のコンテストで使うための置き場）

**このフォルダはテンプレに同梱される** ＝ `new.sh` で作った新しいコンテスト repo にそのままコピーされる。
だから**コンテスト開始時に「過去の自分の分析」が手元にある**。

```
knowledge/
├── README.md          この文書（構造カルテの軸・書き方・索引）
├── contests/          参加記録: 1回1ファイル。結果論ベースの構造分析
└── techniques/        テクニック: 1件1ファイル。**適用条件を構造の軸で書く**
```

## 正本はどこか

- **正本は `~/ahc/template/knowledge/`。** コンテスト repo 側にあるのは**コピー（読み取り専用）**。
- **コンテストが終わったら、参加記録とテクニックを書いて `template/knowledge/` に置く**（正本を更新する）。
  コンテスト repo 側のコピーを編集しても次に伝わらない。

## 3層の棲み分け

| 層 | 場所 | 中身 | 性質 |
|---|---|---|---|
| ルール | `CLAUDE.md` | **毎回必ず従うこと**（一般化済み） | 恒久・短い・根拠は1行 |
| 分析 / 道具 | **`knowledge/`** | **構造カルテと結果論の分析 / 適用条件つきの技術** | 蓄積・詳しい |
| 一次資料 | 各コンテスト repo の `LOG.md` | 生ログ（測定値・経緯・全アプローチ・提出の推移） | private repo に残る |

- **同じ知見が2回目のコンテストで出たら `CLAUDE.md` のルールに昇格させる**（1回だけならここに置く）。
  昇格したらこちら側に「→ CLAUDE.md 済」と印をつける（どちらが正かを迷わないため）。

## 問題の構造カルテ（8軸）

**新しい問題を読んだら、まずこれを埋める。** 目的は「この問題の構造では**どの解法クラスが勝ち、どれが相性が
悪いか**」を、コードを書く前に読み取ること。

> **軸の受入テスト**: AHC068 の構造をこのカルテに書いたとき、**1行もコードを書く前に**
> 「距離ベースの評価関数＋隣接スワップの探索は負ける」と読めること。読めない軸は役に立たない。

### 出力とコスト（ここで解法クラスがほぼ決まる）

| # | 軸 | 見るもの | 何が決まるか |
|---|---|---|---|
| 1 | **出力の型** | 配置・割当 / 操作列（時系列）/ 対話 | 配置なら SA・局所探索が素直に乗る。操作列は状態爆発するので「1つずつ確定する構築」が強い。対話は情報収集と方針切替 |
| 2 | **スコアの単位** | 何が点になるか（品質 / 回数 / 誤差）。log か線形か。**手元で最小化する代理指標と、点になる量が同じ単位か** | 回数が点なら手数最小化ゲーム。log なら全ケース均等に効く。**代理指標の単位がずれていたら、そこで打ち切る** |
| 3 | **1手の威力と副作用** | 1手の到達範囲（距離に依存する/しない）。巻き込み（害か**資源**か）。代数的性質（対合・可換・群） | 距離非依存なら距離ベースの評価は無効。巻き込みが資源なら**共有**が主レバー。対合なら操作列を可塑に保てる |

### 問題の結合

| # | 軸 | 見るもの | 何が決まるか |
|---|---|---|---|
| 4 | **分解と結合** | 独立な部分問題に切れるか。切ったときの**理論下限は上位スコアに届くか** | 「**分解できるが、分解したら数学的に届かない**」を検出する軸。届かないなら結合が必須 |
| 5 | **決定の干渉** | 確定したものが後の自由度を削るか。実行可能性は局所判定か大域か | 削るなら**順序**がレバー。大域制約なら連結性維持などの構造が必要 |

### 入力と資源

| # | 軸 | 見るもの | 何が決まるか |
|---|---|---|---|
| 6 | **ケース分布** | 何が難易度を決めるか。極端なケースで最適戦略が変わるか | 変わるなら戦略分岐、変わらないなら単一戦略に集中 |
| 7 | **入力の乱雑さ** | 活用できる偏り・構造（クラスタ / 周期 / 幾何的近接）があるか。一様ランダムか | 構造があれば前処理・分解・パターン利用が効く。一様ランダムなら**期待値・下限の解析**ができる（軸4に使う） |
| 8 | **制約の余裕と感受性** | **余裕**: TL/メモリに対し1回の構築・評価が何回まわるか。**感受性**: TL を N 倍したらスコアがどれだけ伸びるか（安く実測できる） | **この2つは別物。**余裕があっても感受性が低ければ、多スタートや深い探索は買えない ⇒ 1回の質（構築・データ構造）が支配的。SA/ビームは感受性が高い前提の道具 |

### 「状態・遷移・評価」の位置

**これは9番目の軸ではない。** 軸1〜3で枠組みを選んだ**後**に、その枠組みの内部を書く欄。
先に書くと「探索で解く」という前提が入る（**この3欄はきれいに埋まったまま、何の警告も出さない**）。

## 参加記録の書き方（`contests/ahcNNN.md`）

**結果論ベースで書く。試行錯誤の経過・提出スコアの推移・後から入手した解説は載せない**（それらは一次資料 or
techniques/ 側）。書くのは「**問題がこういう構造だったから、この解法が上位を取れた／これは相性が悪かった**」。

1. **問題の構造カルテ**（上の8軸）
2. **上位が取れた理由** — カルテのどの軸の帰結としてその解法が強いのか
3. **相性が悪かったもの** — どの軸に反していたのか（自分が採った道もここに入れる）
4. **結果** — 最終順位とスコア、上位との差（推移は一次資料へ）
5. **この回で得た道具** → `techniques/` へのリンク

## テクニックの書き方（`techniques/<name>.md`）

- **主張**（1行で何ができるか）
- **適用条件** — **構造カルテの軸の値で書く**（例:「軸1=操作列」かつ「軸3の代数=対合」）。
  これがあると、新しい問題のカルテを埋めた時点で**使える道具が引ける**。
- **効果** — どのコンテストで、どれだけ（測定値）
- **限界・反例** — 効かなかった条件
- **昇格状況** — `CLAUDE.md` のルールにしたなら「→ CLAUDE.md 済」
