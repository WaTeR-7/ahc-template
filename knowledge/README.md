# knowledge/ — 過去コンテストの分析とテクニック（現在のコンテストで使うための置き場）

**このフォルダはテンプレに同梱される** ＝ `new.sh` で作った新しいコンテスト repo にそのままコピーされる。
だから**コンテスト開始時に「過去の自分の分析」が手元にある**。

```
knowledge/
├── README.md          この文書（構造カルテの軸・書き方・索引）
├── contests/          参加記録: 1回1ファイル。結果論ベースの構造分析
├── methods/           **大枠の手法**: ビーム / SA / 時空間BFS …。**この一覧が「手持ち」そのもの**
└── techniques/        テクニック: 手法の中で使う部品。1件1ファイル
```

**`methods/` と `techniques/` の違い**: 手法は**解き方の枠組み**（何を状態とし、何を最適化するか。
これを選ぶと他が決まる）。テクニックは**枠組みの中の部品**（単体では解法にならない）。
迷ったら「これ単体で解答を最後まで作れるか」で判定する。

## 正本はどこか

- **正本は `~/ahc/template/knowledge/`。** コンテスト repo 側にあるのは**コピー（読み取り専用）**。
- **コンテストが終わったら、参加記録とテクニックを書いて `template/knowledge/` に置く**（正本を更新する）。
  コンテスト repo 側のコピーを編集しても次に伝わらない。

## 3層の棲み分け

| 層 | 場所 | 中身 | 性質 |
|---|---|---|---|
| ルール | `CLAUDE.md` | **毎回必ず従うこと**（一般化済み） | 恒久・短い・根拠は1行 |
| 分析 / 道具 | **`knowledge/`** | **構造カルテと結果論の分析 / 手法 / 適用条件つきの技術** | 蓄積・詳しい |
| 一次資料 | 各コンテスト repo の `docs/` | 生ログ（測定値・経緯・全アプローチ・提出の推移） | private repo に残る |

- **同じ知見が2回目のコンテストで出たら `CLAUDE.md` のルールに昇格させる**（1回だけならここに置く）。
  昇格したらこちら側に「→ CLAUDE.md 済」と印をつける（どちらが正かを迷わないため）。

## 問題の構造カルテ（8軸・9欄。軸3 だけ 2 段）

**新しい問題を読んだら、まずこれを埋める。** 目的は「この問題の構造では**どの解法クラスが勝ち、どれが相性が
悪いか**」を、コードを書く前に読み取ること。

> **軸の受入テスト**: AHC068 の構造をこのカルテに書いたとき、**1行もコードを書く前に**
> 「距離ベースの評価関数＋隣接スワップの探索は負ける」と読めること。読めない軸は役に立たない。
> **AHC069 版**: 同じく着手前に「**矩形だけの形族では大口（`P ≥ 81`）は届かない**」と読めること
> ── これは軸3a（条文）では読めず、**軸3b(b)（入力の端）を測って初めて読める**。新しい軸を足すときは、
> **過去の失敗がその軸で捕まるか**を必ず当てる。
> **AHC072 版**: 「**1 手ずつのビームは、一時的な悪化を含む手順を拾えない**」と読めること
> ── 🔴 **これは 8 軸では読めない**（カルテは「手数を直接数える構築が本命」まで正しく読んでいたのに、6 日かかった）。
> 軸を足すのではなく、**カルテの次の段として「性質 × 解法の表」を書く**（下の節）。

**カルテは一度に埋まらない。埋まる順に3段ある**（埋まっていない軸を空欄のまま放置しないための目印）:

| いつ埋まるか | 軸 |
|---|---|
| **問題文だけで埋まる**（着手前・ここが本番） | **1 出力の型 / 2 スコアの単位 / 3a 1手の威力 / 3b(a) 条文の端 / 5 決定の干渉 / 7 入力の乱雑さ** |
| 安い測定で埋まる（実行可能解ができた直後） | 🔴 **3b(b) 入力の端**（入力を1回走査するだけ。**ahc069 はここを 10 日落とした**）/ **6 ケース分布**（seed 掃引の分布）/ **8 余裕と感受性**（TL を N 倍して2回走らせる） |
| 順位表が出てから埋まる | **4 分解と結合**（独立解の天井 ⇔ 上位スコア。天井の計算自体は軸7 が埋まれば着手前にできる） |

⇒ **軸4 は「天井を先に計算しておき、上位スコアが見えた時点で突き合わせる」**のが正しい使い方。
ahc068 では天井（2.345手/枚 = est 1011M）を着手前に出せたのに計算しておらず、上位と比べる機会を逃した。

### 出力とコスト（ここで解法クラスがほぼ決まる）

> **最終列「自分の実装」は空欄で放置しない。** カルテは*問題*を記述するが、**過去 2 回の一番の失敗は 2 回とも
> *実装*の側にあった**（ahc068: 配達を距離最短で実装 / ahc069: fit 条件を外接矩形全部空きに）。
> **どちらもカルテは正しく埋まっていた。** ⇒ 各軸に「その軸に対して自分が何を選んだか」を紐づけ、
> `docs/NOW.md` の register に落とす。**レバーが全滅したら、まずこの列を上から疑う。**

| # | 軸 | 見るもの | 何が決まるか | 自分の実装（→ register） |
|---|---|---|---|---|
| 1 | **出力の型** | 配置・割当 / 操作列（時系列）/ 対話 | 配置なら SA・局所探索が素直に乗る。操作列は状態爆発するので「1つずつ確定する構築」が強い。対話は情報収集と方針切替 | 解を何で表すか |
| 2 | **スコアの単位** | **(a) 1ケース内**: 何が点になるか（品質 / 回数 / 誤差）。log か線形か。**手元で最小化する代理指標と、点になる量が同じ単位か**<br>**(b) ケース間の集計**: 絶対和 / **相対（`1e9 × 自分/全参加者最大`）** / log | (a) 回数が点なら手数最小化ゲーム。**代理指標の単位がずれていたら、そこで打ち切る**<br>🔴 (b) が**判定プロトコルを丸ごと決める** ── 相対評価なら**絶対スコア和で採否を決めてはいけない**（`CLAUDE.md` の「相対評価のコンテストでの判定」節へ） | 代理指標は何か / 採否をどの統計で見るか |
| 3a | **1手の威力と副作用** | 1手の到達範囲（距離に依存する/しない）。巻き込み（害か**資源**か）。代数的性質（対合・可換・群） | 距離非依存なら距離ベースの評価は無効。巻き込みが資源なら**共有**が主レバー。対合なら操作列を可塑に保てる | 1手をどう実装したか |
| 3b | 🔴 **1手の可否（前提）** | **(a) 条文の端**: パラメータの端（幅1 / 最小サイズ / 上限いっぱい / degenerate）が合法か<br>**(b) 入力の端**: 入力を 1 回走査して分かる幾何的な上限（例: 全部芝生の最大正方形） | **条文が許す*最も強い操作*を primitive にし、条文が要求する*最も弱い条件*を可否の判定式にする。**<br>(b) が「その手を**そもそも到達可能か**」を決める | **可否の `if` そのもの**（ここが register の行） |

**なぜ 3 を割るか（受入テストに落ちたから）**: 上の受入テストを ahc069 で当てると
「カルテを書いたら『**矩形だけの形族では大口は届かない**』と読めるか」になるが、**読めなかった**。
軸3 が**条文の側だけ**を向いていて、効いたのは**入力の幾何**（全部芝生の最大正方形が 6〜8 ⇒ `P ≥ 81` は
空の盤面でも `L_min` 不可）だったため。**入力を 1 回スキャンすれば着手前に分かった**のに、測ったのは 10 日後。
ahc068 の失敗（`w=1` の見落とし）は (a)、ahc069 は (b) ⇒ **同じ軸の別の半分を 1 回ずつ落としている。**
⚠ 番号を振り直さないのは、既存の「軸1〜3で解法クラスが決まる」と 30 箇所以上の軸4〜8 参照を壊さないため。

### 🔴 軸4 と軸8 は「値」ではなく「測った日 / 版 / 再測定トリガ」を書く

この 2 軸だけは**版が進むと値が動く**。1 個の数字を書いて放置すると、**古い天井で投資判断をする**ことになる。

| | ahc069 で実際に動いた例 |
|---|---|
| 軸4（天井） | ビームの天井 **+2.003%** → 機構を積んだ後に測り直したら **+0.278%**（**86% が既に回収済み**だったのに、古い値のまま提案した） |
| 軸8（感受性） | 候補数の感受性は序盤 **+3.956%**（blob の種 16→256）→ 終盤は **±0.1%**（飽和。増やしても減らしても動かない） |

⇒ 書式は `値（測定日 / 版 / 再測定トリガ）`。**再測定トリガ**の例: 「新しい候補生成を入れたら」「速度が 2 倍になったら」。
**未実装のまま温めている候補の天井も、別の機構を入れたら測り直す。**

### 🔴 カルテの次の段: 性質 × 解法の表（序盤の 2〜3 日で書く）

カルテは「どの族が向くか」までを言う。**具体的な解法クラスの候補どうしを比べるのは、この表**:
行 = 問題の性質（カルテの軸から来るもの ＋ **「良い解はどんな形か」から来るもの**）、列 = 解法クラスの候補、
セル = **○ 近似なしで扱える ／ △ 規則・近似に任せている ／ × 扱えない** と理由 1 行。

- **「原理上は全部の手を検討している」は ○ の根拠にならない**（幅が有限なら、評価が低く見る手順は拾われない）。
- **△ のセルが、そのクラスで探索から動かせない損**になる。全部 ○ の列が無ければ、その列を作れないかを問う。
- **上位に届かないと確定したら、その日のうちにこの表を書き直す**（同じクラスの中の改良はその後）。
- 小さな入力での検証は、大きな入力でしか現れない性質を写さない ⇒ 「小さな入力では」と前提を付ける。

書き方と実例（ahc072）は [`techniques/property-method-table.md`](techniques/property-method-table.md)。表は `docs/SETUP.md` に置く。

### 「状態・遷移・評価」の位置

**これは9番目の軸ではない。** 軸1〜3で枠組み（＝`methods/` のどれか）を選んだ**後**に、
**その手法の記事の「中身」欄**に書くもの。カルテの段で先に書くと「探索で解く」という前提が入る
（**この3欄はきれいに埋まったまま、何の警告も出さない** ── AHC068 で負けた枠組みは
「状態=盤面 / 遷移=隣接スワップ / 評価=距離和」で完全に記述でき、しかも何も警告しなかった）。

## 手法の書き方（`methods/<name>.md`）

**「ビームサーチとは」を説明する記事ではない**（それは他所にある）。**自分が使えるようにするための記事**。

1. **一言で**（何を最適化する手法か）
2. **他の手法との対比** ── 特に**何を最適化するか / 状態 / 方向を決めるもの / 時間を増やすと伸びるか**。
   ここが一番役に立つ（別の族に迷い込んだ時に気づける）
3. **いつ使うか** ── カルテの軸で。**向かない条件も書く**
4. **中身**（状態・遷移・評価。ここが「状態・遷移・評価」の正しい置き場）
5. **骨格**（漸化式・擬似コード。次回そのまま写せる粒度で）
6. **実装の要点 / 調整点**（env で外出しするノブと、掃引で決まった値）
7. **落とし穴**（自分が踏んだもの）
8. **実績**（どのコンテストで、どれだけ）
9. **別名・関連**（一般的な呼称があれば。検索できるようにする）

## 参加記録の書き方（`contests/ahcNNN.md`）

**結果論ベースで書く。試行錯誤の経過・提出スコアの推移・後から入手した解説は載せない**（それらは一次資料 or
techniques/ 側）。書くのは「**問題がこういう構造だったから、この解法が上位を取れた／これは相性が悪かった**」。

1. **問題の構造カルテ**（上の8軸・9欄）
2. **上位が取れた理由** — カルテのどの軸の帰結としてその解法が強いのか
3. **相性が悪かったもの** — どの軸に反していたのか（自分が採った道もここに入れる）
4. **結果** — 最終順位とスコア、上位との差（推移は一次資料へ）
5. **この回で得た道具** → `methods/` / `techniques/` へのリンク

## テクニックの書き方（`techniques/<name>.md`）

- **主張**（1行で何ができるか）
- **適用条件** — **構造カルテの軸の値で書く**（例:「軸1=操作列」かつ「軸3の代数=対合」）。
  これがあると、新しい問題のカルテを埋めた時点で**使える道具が引ける**。
- **効果** — どのコンテストで、どれだけ（測定値）
- **限界・反例** — 効かなかった条件
- **昇格状況** — `CLAUDE.md` のルールにしたなら「→ CLAUDE.md 済」
