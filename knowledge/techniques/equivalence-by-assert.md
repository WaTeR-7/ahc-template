# 核を書き換えるときは、byte 一致ではなく assert で同値を取る

**主張**: **旧実装を消さずに残し、実走行中に同じ入力で新旧を両方評価して `assert!(旧 == 新)`。**
通ってから旧を捨てて拡張する。**byte 一致（`same.sh`）が使えない「核の書き換え」に対する同値検査**。

## なぜ要るか（byte 一致の構造的な盲点）

「新機構 OFF で前版と byte 一致」は**機構を足す**ための道具として強力だが、**通すには既存コードを触らず
分岐を足すしかない**。⇒ 規律が**追加に報酬・置換に罰**を与え、しかも

- **既定 OFF** が増幅する（積み上がるのは「初日の核 ＋ N 本の任意分岐」）
- **鎖が推移的**（`97←98←99…` の不動点は**版1の決定**）

⇒ **初日に書いた核が全分岐の共通項として凍り、どの A/B 比較にも写らない。**

🔴 実測: ahc069 の fit 条件（`free_box`）は **124 版中 123 版に存在し、最古は初日の版**。
10 日間 + 延長戦を通して一度も書き換えられず、**緩めた瞬間に `Δlog +1.19%`**（その回の単発 2 位）。

## 使い分け

| | **byte 一致**（`same.sh`） | **assert 同値** |
|---|---|---|
| 目的 | **機構を足す** | **核を書き換える** |
| 比べるもの | 最終出力（外から） | 内部の値（中から） |
| 失敗時に分かること | 「違う」だけ | 🔴 **どの入力で・どちらが・いくつ違うか** |
| 前提 | 新機構を OFF にできる | **旧実装を残せる**（同じ量を 2 通りで計算できる） |
| コスト | 20 seed 走らせるだけ | 実行が重くなる ⇒ **検査用 env で ON**（`AHC_XCHK=1`） |

**両方使う。** 新版はまず「検査 env を切れば前版と byte 一致」を確認し、**検査 env を立てて assert を通す**。

## 型（手順）

1. **旧実装を消さない。** 新実装は隣に置く（関数を分ける）。
2. 検査 env（例 `AHC_SHCHK=1`）で、**本番の入力分布・実走行の中で**両方を評価して比較する。
   ⚠ 合成入力ではなく**実ケースで回す**（核が壊れるのは実データの端）。浮動小数なら誤差幅を決める（`1e-9` 等）。
3. **食い違ったら、それが発見。** 直す前に**なぜ違うのかを説明する**（下の実例 2 参照）。
4. 20 seed 通ったら新実装に一本化し、**そこから初めて拡張する**（拡張してから検査すると、
   食い違いが「バグ」なのか「拡張ぶん」なのか切り分けられなくなる）。
5. 検査 env は**残す**（既定 OFF）。次に核を触るとき再利用できる。

## 実例

**① 整数キー化（ahc069 `28_ikey`）** ── 「f64 の比較だから整数化できない」と机上で結論していたが、
**状態空間が小さければ全数検証できる**。起動時に総当たりで f64 と整数キーの順序一致を検査し、
食い違えば panic。⇒ **単発 −19.8%（速度）** と、「理論的に無理」という誤結論の破棄。
副産物として **掃引の plateau から「実装が有利な値」を選べる**ようになった（`DTW` を 0.2 → 0.25 にずらすと
byte 一致を保ったまま整数化できた）。

**② 位置評価の一般化（ahc069 `104_shape` / `AHC_SHCHK=1`）** ── 形族を広げるために評価式を
「行区間形の一般形」に書き直した。旧式（5 セグメント直書き）と**全候補で突き合わせて assert**したところ、
**fit を緩めた条件でだけ食い違った**。原因は「外接矩形の未使用セルが**利用中グループでありうる**」ことで、
旧式はそのセルを露出でしか見ておらず、時刻ペナルティに計上していなかった ──
🔴 **食い違いそのものが「fit を緩めると何が変わるか」の発見だった。** byte 比較なら「違う」で終わっていた。

## 落とし穴

- **「一致しないのが正しい」場合がある。** ②では `fit=false`（旧前提）でだけ一致し、`fit=true` では
  一致しない方が正しかった。⇒ **検査に適用条件を書く**（`if chk && !fit { assert!(...) }`）。
  条件を書かずに「直して一致させる」と、**改善を潰す**。
- **検査が重い。** 候補ごとに 2 度評価するので、検査 env は必ず分ける（既定 OFF）。
- **旧実装を早く消しすぎない。** 消した瞬間にこの道具が使えなくなる。

## 適用条件

**問題の構造に依らない（プロセスの道具）。** 必要なのは「**同じ量を 2 通りで計算できる**」ことだけ。
逆に言えば、核の書き換えを **「同じ量の別実装」の形に落とせるかどうか**が使えるかの判定になる。

**実績**: ahc069 で 2 回（整数キー化 / 位置評価の一般化）。うち 1 回は**食い違いを実際に検出**した。
