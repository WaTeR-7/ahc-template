# `.max()` / `.clamp()` は env レバーを黙って殺す

**主張**: **チューナブルを env で外出ししても、その値が床・天井に飲まれていれば掃引は何も測っていない。**
しかも**過去の掃引の解釈まで遡って壊れる** ── そのとき測っていたのは「レバーの値」ではなく
**「床に当たるか否か」**だったことになる。
⇒ 🔴 **掃引を投入したら、まず「その env が実際に何になったか」を 1 回印字して目視する。**

## 典型的な形

```rust
let t = (base * mult).max(FLOOR);   // base は入力ごとに何桁も振れる量
```

`base * mult` が常に `FLOOR` 未満なら、`mult` を掃いても出力は 1 バイトも変わらない。
**掃引は「差が無い」ではなく「レバーが存在しない」を測っている**が、表には `null` としか出ない。

## 適用条件（構造カルテの軸で）

- **軸に依らない**（プロセスの道具）。
- 危険度が上がるのは、**実測値から自動計算する量**（温度・閾値・予算）に安全弁を付けたとき。
  定数を直接 env にしている箇所では起きない。

## 手順

1. レバーを足したら、**そのレバーが最終的に取った値**を診断行に出す（1 行）。
2. 掃引の 1 本目が出た時点で**その値が設定ごとに違うことを確認する**。同じなら掃引を止める。
3. 🔴 床・天井を残すなら**床そのものを env にする**（`FLOOR` も掃ける形にする）。
   残さないなら消す ── **「安全のため」で入れた床は、安全ではなく無効化として働くことがある。**

## なぜ見つけにくいか

- **出力は変わらないので失格もエラーも出ない。**
- **`null` は「効かないレバー」の顔をしている** ── 否定の棚に載って、そのまま何日も生き延びる。
- 床に当たる/当たらないが**入力ごとに違う**と、掃引の値が「効果」ではなく
  **「床に当たった入力の割合」**になり、非単調な応答に見える（そこで「峰がある」と誤読する）。

## 限界・反例

- 床が**実際に必要な場合**（0 除算・発散の回避）はある。その場合も**発火率を数える**。
  発火が常時 100% なら、それは床ではなく**定数**である。
