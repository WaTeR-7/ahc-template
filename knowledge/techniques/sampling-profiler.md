# 内側ループの中の割合は、命令の番地を採って測る

**主張**: **細かい区間ごとにタイマーを挟む計測は、軽い段を水増しする。** 内側ループの中で何が高いかは、
**命令の番地を一定間隔で採る方式**（SIGPROF ＋ addr2line）で、関数・行ごとの割合として出す。
道具は `lib/sprof.rs`（貼る）と `scripts/sprof.py`（集計）。外部の道具は要らない。

## 適用条件

- 段の割合までは `lib/prof.rs`（回数 × 1 回あたり）で分かったが、**その段の中で何が高いか**が分からない
- 1 回が数十 ns〜数百 ns の処理を、数百万回まわしている（タイマーの読み出し自体が無視できない）
- **軸8 の感受性が残っている**（速くした分が伸びに変わる）。⚠ 先に、同じ版の時間を N 倍にして「速さの価値」を測る

## 実例（ahc072 の入れ直しの DP）

出来事ごとに rdtsc を挟むと、「何もしない出来事の通過」が DP の **3〜4 割**に見えた。番地を採ると実際は **1 割前後**で、
本命は別の段（操作列の再生が全体の半分）だった。そこから:

| 変更 | 効果（時間） | 種類 |
|---|---|---|
| DP の費用の上限を 0 → 1 → 2 → 4 … と上げ、見つかった所で止める | −42% | 考え方を変える |
| 必要条件での枝刈り（乗り継ぎだけで着ける位置・時刻でだけ状態を作る） | −17% | 考え方を変える |
| 操作列の再生をまとめる | （全体の半分の段） | 考え方を変える |
| 細かい削り | −5〜−11% | — |
| 空振り・逆効果 | 2 本 | — |

合わせて 3.7 倍。**効いたのは考え方を変える変更**で、細かい削りが ±数 % で符号も読めなくなった所で打ち切った。
スコアへの効果は +2.4%、速さに合わせて設定を測り直して +0.76%。

## 使い方

1. 計測用の版を別ファイルに作る（`NNs_samp.rs`）。`mod sprof` を貼り、測りたい区間の前後に `sprof::start(200)` と `sprof::dump(path)`。
   **出力は元の版と同じ**（byte 一致を確認する）。
2. debug 情報つきでビルド（最適化はそのまま。**掃引中の `target` を汚さない場所へ**）:
   `CARGO_PROFILE_RELEASE_DEBUG=2 cargo build --release --bin <bin> --target-dir <別の場所>`
3. `PROF_OUT=<file>` を付けて、**何十件か**走らせる（決定的な設定で）。
4. `python3 scripts/sprof.py <bin> src/bin/<bin>.rs <file>... [--names 段の関数名,…]`

## 限界・落とし穴

- 🔴 **標本の間隔はカーネルの刻みで決まり、要求より粗い**（WSL2 では 200 µs を要求しても 1 秒に約 100 個）。
  1% の段を読むには数千個要る ⇒ 件数で稼ぐ。
- x86_64 Linux 専用（シグナルの文脈の中の命令の番地の位置を決め打ちしている）。
- 共有ライブラリ（libm など）の中は `??` と出る。
- **「回数が多い」も「同じデータを何度も走査している」も、削る理由にならない**（ahc069 で 2 連続で外した）。番地で割合を見てから削る。
- 🔴 **「たまにしか起きないはず」の処理は、提出する最終解ではなく、探索の途中の悪い解で数える**
  （ahc072 の焼きなまし: 非常手段は最終解では 0 回だが、途中の計画では 1 回の評価に 20〜40 回起きていて、評価時間の 28〜66%）。
- 探す順・範囲を変える高速化は乱数の列が変わるので、byte 一致の代わりに最適値の一致を assert する
  （→ [核の書き換えは assert で同値を取る](equivalence-by-assert.md) の実例 ③）。
