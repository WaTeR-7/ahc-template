# 分解した部分問題に、既存分野の名前を付けてみる

**主張**: 問題を分解したら、各部分に **「これは何問題か」の名前**を付ける。
名前が付いた瞬間に、その分野の標準アルゴリズムが棚から取れる。
**自作の近傍を書き始める前にやる。**

## やり方

構造カルテを埋めたら、各部分問題に対して候補の名前を当ててみる。

| 名前 | 特徴 | 棚から取れるもの |
|---|---|---|
| **配線 / ルーティング** | 端点の組を、容量制約のある資源の上で結ぶ | **negotiated congestion**（rip-up して混雑コストを反復ごとに上げ、競合を解消する）、多品種フロー |
| **マッチング** | 2 部・一般グラフの対応付け | Hungarian、Blossom、貪欲＋交互路 |
| **被覆 / 分割** | 全要素をちょうど 1 度使う | 集合被覆の LP 緩和、Exact Cover |
| **スケジューリング** | 資源と時間の割当 | リスト法、EDF、緩和＋丸め |
| **割当 / 配置** | 位置を選ぶ | 局所探索、線形緩和 |

⚠ **名前を付けるのは「解法を丸ごと持ってくる」ためだけではない。**
その分野で**何が難しいとされているか**が分かるのが大きい
（配線なら「順番依存で先に引いたネットが有利」＝ だから rip-up が要る、など）。

## 見分け方 ── 名前を付け損ねているサイン

- **その部分問題を解く関数を自分で書いている**のに、名前を考えたことがない
- 書いたものが**単発の手**で、反復して収束させる構造になっていない
- 「候補が見つからない」「競合する」といった症状を、**探索の乱数で殴っている**

## 限界・反例

- 名前が付いても、**制約が微妙に違う**ことが多い。そのままは使えない。
  ⇒ **骨格（反復の形・コストの上げ方）だけ借りて、中身は問題に合わせる。**
- 部分問題として切り出すと**全体最適から離れる**。切り出す価値があるかは、
  切り出した側を最大化したときに元の目的がどうなるかで判断する
  （→ [積の目的関数を 2 段に割る](two-phase-product-objective.md)）。

## 実績

MM166 の「exit のペアを盤面に配線する」は、名前を付ければ**容量制約つきのルーティング**で、
FPGA のグローバル配線そのものだった。上位解は negotiated congestion をそのまま使っている。
自分は単一ネットの Dijkstra を書いて**焼きなましの中の一手**にしており、
**部品は持っていたがアルゴリズムになっていなかった。** 順番も逆で、
上位解は配線を**先に完結**させてから改善段に渡している。
