# 速度・計算量を攻めるとき

> **これは `CLAUDE.md` の規則の「長い版」**（根拠・失敗例・数字つき）。`CLAUDE.md` には短い形だけがある。
> **いつ読むか**: 高速化・プロファイル・時間予算の再配分に入る前。
> 規則を足すとき・直すときは、**長い版をここに書き、`CLAUDE.md` には 1〜2 行だけ**置く（両方に全文を書かない）。
> 文中の `EX###`・`NG##`・`DC##` は、その回の private repo の `docs/` の ID。

> ahc069: 10 段で −51.4% ／ 空振り 2 本。ahc072: 入れ直しの DP を 3.7 倍。

- **推測で削らず全数監査する**(`lib/prof.rs` を貼って `ON=true`)。**回数と1回あたりを分けて出す**まで
  削り所は見えない(ahc068: 同じホットループ内の O(N) 19.7M回 と O(1) 25.3M回。間引くべきは前者だった)。
  **回数が多い ≠ 高い**(ahc069: 本命は推測と別の段で 56〜85%)。
- 🔴 **「たまにしか起きないはず」の処理を疑う。提出する最終解ではなく、探索の途中の悪い解で数える**(ahc072: 誰も動けないときの非常手段は最終解では 0 回だが、
  焼きなましの途中の計画では 1 回の評価に 20〜40 回起きていて、評価時間の 28〜66%。しかも入力だけで決まる量(巣からの距離)を毎回 BFS で求めていた ⇒ 最初に 1 回だけ計算して −51〜−63%。EX213)。
- **🔴 段の割合が分かっても「その段の中で何が高いか」は別問題。「同じデータを何度も走査している」は削る理由にならない。**
  ahc069 で 2 連続で外した: ① 狙った項は段の 17% のうち 7% ② L1 に乗る 2500B を 3 走査 → 1 本に融合したら
  **+0.9% で悪化**(コストは読み込みでなく書き込みと計算。**融合は依存を増やしてベクトル化を阻害する**)。
  ⇒ **段の中をもう一段割って測る。**
- **🔴 「f64 の比較だから整数化できない」と机上で決めない。状態空間が小さければ全数検証できる**
  (ahc069: 評価を整数キー 1 本に畳んで **単発 −19.8%**)⇒ **総当たりを起動時に回すだけで可否が確定する。**
  食い違う値では panic させる([`knowledge/techniques/equivalence-by-assert.md`](../techniques/equivalence-by-assert.md))。
- **掃引の plateau(同一結果の平坦域)からは「実装が有利な値」を選べる**
  (ahc069: 既定を 0.2 → 0.25 にずらすだけで byte 一致を保ったまま整数化できた)。
- **内側ループの「1 要素あたり ns」まで測れたら、byte 一致で削れる余地は尽きたと判断してよい**
  (そこから先は呼び出し回数を減らす話で、**それはスコアに影響するレバー**)。
- **配分と計算量を混同しない**(ahc069: 配分では +0.28% が上限 → 計算量を直したら +0.70%)。
  **高速化そのものの Δ は 0.000%(byte 一致)で、価値は「空いた予算」にしか現れない** ⇒ **レバーとセットで評価する。**
- **🔴 壁時計で打ち切っている段が残っていると、高速化は「予算」にならない**(下流がその締切まで多く働くだけ)。
  **作業量カウンタで打ち切る段でだけ高速化が予算になる**(ahc069: 素の時間 −8.79% を作っても、
  ローカルのスコアも裾も動かなかった。⚠ ただし**ジャッジ側では裾に出た** ── 自分の seed 集合に重い例が無かっただけ)。
- 🔴 **細かい区間ごとにタイマーを挟む計測は、軽い段を水増しする**。命令の番地を一定間隔で採る方式（`lib/sprof.rs` ＋ `scripts/sprof.py`。SIGPROF ＋ addr2line で、外部の道具は要らない）で関数・行の割合を出す
  （ahc072: 出来事ごとに rdtsc を挟むと「何もしない出来事の通過」が DP の 3〜4 割に見えたが、実際は 1 割前後で、本命は別の段（手の列の再生が全体の半分）だった。EX239）。
- 🔴 **乱数の列だけが変わる高速化（探す順・範囲を変える）は、byte 一致の代わりに「同じ入力で旧・新の最適値が同じ」を assert してから入れる**（乱数は巻き戻す。ahc072: DP の上限を小さい値から順に上げる −42%・
  必要条件での枝刈り −17% を、最小費用の一致 113 万 ＋ 270 万回で確かめて入れた。EX239）。**byte 一致が外れたら原因を 1 件まで追う** ── 外れた 2 回とも、DP が暗に持っていた規則が見つかった。
- **効くのは考え方を変える変更**（ahc072: 上限を順に上げる・再生をまとめる・枝刈りが −17〜−42%、細かい削りは −5〜−11%、空振りと逆効果が 2 本）。細かい削りが ±数 % で符号も読めなくなったら打ち切る。
- **🔴 空いた予算の再配分は「使い先の機構」が決まってから行う**(機構を入れると最適点が動く)。
